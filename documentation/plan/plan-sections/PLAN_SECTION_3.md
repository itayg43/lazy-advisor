## Section 3: Stage 1 — Clarify

**Goal**: Given raw goal text, calls OpenAI (Responses API) with `ask_user` tool, asks adaptive questions, produces validated UserProfile via structured output.

**Reference**: OpenAI Responses API — client singleton, `responses.parse()` with `zodTextFormat()`, status + `output_parsed` validation, token usage via `input_tokens`/`output_tokens`, `temperature: 0` for deterministic structured output.

### Design Decisions

- **Responses API over Chat Completions** — native tool calling and structured output via `responses.parse()`, less manual work than `chat.completions`. Trade-off: fewer community examples
- **Client/service split for OpenAI** — `openai.client.ts` exports the singleton, `openai.service.ts` exports `callOpenAI` / `callOpenAIParsed`. Service accepts `ResponseCreateParamsNonStreaming` directly (no custom wrapper types). Callers build the full prompt object including model, instructions, tools, `previous_response_id`, and `text.format`
- **`callOpenAI` vs `callOpenAIParsed`** — tool-calling (`responses.create`) and structured-output extraction (`responses.parse`) have different validation needs. `callOpenAIParsed<T>` uses a generic type param — the caller passes `zodTextFormat` inside params and the SDK handles parsing via `responses.parse<Params, T>()`. Trade-off: `T` is unconstrained, but callers are internal stages
- **`OpenAIResponse<T>` as the unified return type** — both functions return `{ id, output, usage }` instead of the full SDK `Response`. `id` for `previous_response_id` chaining, `output` is `ResponseOutputItem[]` or `T`, `usage` for token logging
- **Error handling** — See [CONVENTIONS.md — Error Handling](../../CONVENTIONS.md#error-handling). Section-specific: `APIError` and non-completed status → `ServiceUnavailableError`, missing `output_parsed` → `InternalError`, non-API errors rethrow unchanged
- **Callback-based `ask_user` tool** — handler receives `sendToUser` + `waitForResponse` callbacks, decoupled from transport. Testable with mocks, transport wired in Section 8. Arguments validated with a co-located Zod schema (`AskUserArgsSchema`); malformed LLM output throws `InternalError`
- **Tool name guard in stage loop** — the Phase B inner loop verifies `functionCall.name === "ask_user"` before dispatching. Unexpected tool names throw `InternalError` to catch model hallucinations early
- **Stage cap (`MAX_STAGE_TOOL_CALLS`) throws `InternalError`** — prevents runaway loops if the model keeps asking questions. Instead of proceeding to extraction with potentially incomplete data, throws `InternalError` to fail fast. Downstream stages depend on a complete profile, so partial extraction would produce unreliable recommendations. Cap check is inside the inner `for` loop (not just the outer `while`), so it fires immediately per tool call even when the model returns multiple function calls in a single response
- **`previous_response_id` does NOT carry `instructions` forward** — the OpenAI SDK JSDoc explicitly states: "the instructions from a previous response will not be carried over to the next response." All chained `callOpenAI` calls in the Phase B loop must re-pass `instructions`. Omitting them caused the model to run without the system prompt, which was the root cause of the model accepting vague timeline values and generating unsolicited advice
- **Dynamic enum injection in prompts** — risk tolerance and knowledge level enum values are derived from their Zod schema definitions (`RiskToleranceEnum.options`, `KnowledgeLevelEnum.options`) rather than hardcoded in prompt strings. Keeps the prompt in sync with the schema automatically. Pattern borrowed from ai-task-assistant's dynamic prompt configuration
- **"Map to closest match" for categorical fields** — the clarify prompt instructs the model to map behavioral descriptions to the closest enum value (e.g., "a 20% drop would stress me but I wouldn't sell" → moderate) rather than requiring the user to say an exact term. The extraction prompt handles the final mapping. This prevents the model from looping on fields where the user gave a valid but indirect answer
- **Field Validation section in clarify prompt** — inspired by ai-task-assistant's "Input Validation" pattern: a dedicated prompt section with explicit rejection criteria and negative examples for vague inputs ("long-term", "short-term", "a while" are NOT specific enough for timeline). Separates field-level validation rules from general instructions
- **`reasoning: { effort: "low" }` on Phase A and B** — reasoning models (gpt-5.4-mini) don't support `temperature`; the `reasoning.effort` parameter controls determinism instead. Low effort is sufficient because the prompt's Field Validation section and examples are explicit enough that the model doesn't need heavy chain-of-thought. Tested 3/3 passing with lower token usage and faster runs (5-7s vs 7-18s with medium)
- **`gpt-5.4-mini` for all phases** — the original switch from mini to gpt-5.4 (during prompt iteration) didn't improve results because the real issue was missing instructions in Phase B. With instructions properly passed and prompt optimized, mini works correctly and is significantly cheaper/faster (~7-12s vs ~59s)
- **`previous_response_id` for conversation state** ([docs](https://developers.openai.com/api/docs/guides/conversation-state)) — pass the previous response ID instead of manually building an input array. OpenAI maintains history server-side. Considered alternatives: (1) manual input array — same token cost since the model processes the same history either way, just more boilerplate; (2) Conversations API — adds persistent cross-session state we don't need (our pipeline runs are short-lived, not multi-session). Compaction ([docs](https://developers.openai.com/api/docs/guides/compaction)) is unnecessary because our stage architecture already keeps each conversation chain short (~10 turns max in clarify)
- **Function call results via `previous_response_id`** ([docs](https://developers.openai.com/api/docs/guides/function-calling)) — when pushing tool results back, use `input: [{ type: "function_call_output", call_id, output }]` combined with `previous_response_id` instead of accumulating a full input array. The `call_id` from the `ResponseFunctionToolCall` ties each result to its tool call. Tool handlers return the result string; the stage loop (3.6) pairs it with `call_id` and sends the follow-up request
- **HTTP over streaming for OpenAI calls** — our stages are tool-heavy (short JSON tool calls), not long prose generation, so users won't notice per-token latency. Streaming complicates tool call handling (must buffer partial `arguments` JSON). We already stream to users via WebSocket (Section 7–8) for progress events. Streaming from OpenAI can be revisited as an optimization for the plan output stage (Section 5) if needed
- **Combined UserProfileSchema** — the original schema (3.1) had 6 fields (`goal`, `currency`, `monthlyBudget`, `riskTolerance`, `investmentHorizon`, `knowledgeLevel`). Updated in 3.6 to combine the best of the original and WORKFLOW.md's spec: 11 fields total (`goal`, `amount`, `age`, `riskTolerance`, `timeline`, `location`, `knowledgeLevel`, `brokerage`, `hasEmergencyFund`, `hasDebt`, `monthlyContribution`). Dropped `CurrencyEnum` and `currency` (inferred from location), renamed `investmentHorizon` → `timeline`, replaced `monthlyBudget` with `amount` + `monthlyContribution`. `brokerage` is required with a default of `"none"` to avoid optional checks downstream
- **Model defined inline with prompt params** — the model string (`gpt-5.4-mini`) is part of the prompt configuration, not a global config setting. Each stage's prompt params (model, reasoning effort, instructions, tools, output format) form a cohesive unit. This supports future versioning — prompt versions can pin different models without global config changes
- **Built-in web search over Tavily** ([docs](https://developers.openai.com/api/docs/guides/tools)) — OpenAI's `{ type: "web_search" }` tool eliminates the need for a separate Tavily client, mock, error class, and search tool handler. Trade-off: less control over search queries and results (black box). Acceptable for a portfolio project; if research quality is insufficient, Tavily is the fallback. See Section 4 for updated plan
